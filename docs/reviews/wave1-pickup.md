## Yang sudah benar (diverifikasi sendiri di kode + DB, bukan dari laporan implementer)

### Keamanan kode (checklist 1)

- **Plaintext tidak pernah disimpan.** Lookup memakai `code_hash` = HMAC-SHA256(`AUTH_SECRET`, kode ternormalisasi) 64 hex (`pickup.service.ts:767-771`), DB CHECK `pickup_credentials_hash_check` menegakkan bentuknya, dan index unik global mencegah duplikat. `code_ciphertext` = AES-256-GCM base64(iv12|tag16|ct) (`:774-797`) hanya untuk tampil ulang pemilik. Probe saya: `code_hash` 64 hex, `ciphertext` **tidak** memuat plaintext, `order_events.metadata` dan `audit_events.metadata/reason` **tidak** memuat plaintext.
- **Tidak ada log.** Tidak ada `Logger`/`console` di seluruh `src/modules/pickup/**`; pino hanya me-redact header authorization/cookie (`src/config/core.module.ts:22-30`) dan tidak mencatat body. Kode tidak pernah ditaruh di URL/query (selalu body), sehingga tidak bocor ke access log.
- **Entropi & panjang:** alfabet Crockford 30 karakter tanpa 0/1/I/L/O/U, panjang 8 → ~6,6×10¹¹ (`pickup.constants.ts:19-20`), dibangkitkan `randomInt` (CSPRNG). Wajar untuk TTL 2 jam + rate limit.
- **Perbandingan deterministik benar:** normalisasi (uppercase, buang non-alnum) dilakukan **sebelum** hashing di kedua jalur (`verifyCode` `:395`, `handover` `:467`), sehingga kode yang diucapkan/diketik dengan spasi/huruf kecil tetap cocok (diuji).
- **Tidak ada kebocoran kode orang lain:** rute buyer hanya membaca kredensial milik order dengan `o.buyer_id = $2` (`:565-572`); tidak ada endpoint staf yang mengembalikan plaintext (staf hanya memverifikasi).

### Otorisasi & scope (checklist 2)

- Kelima rute memakai `AuthGuard` di level controller (`pickup.controller.ts:28`, `tenant-pickup.controller.ts:42`); `PickupModule` terdaftar di `app.module.ts:36`.
- Semua aksi staf memakai `AccessService.requireTenant(actor, tenantId, 'tenant.orders.handover', client)` **di dalam transaksi mutasi** (`:146-151`, `:308-313`, `:469-474`); `markHandedOver` memeriksa ulang permission (defense in depth). Staf `pickup` yang hanya punya `tenant.orders.read`+`handover` lolos, kitchen (accept/prepare) ditolak — diuji.
- Setiap query staf di-scope `tenant_id`; order/kredensial tenant lain → **404** (`:624-629`), bukan 403, sehingga eksistensi tidak bocor (diuji untuk verify dan handover).
- Buyer hanya dapat membaca kode order miliknya; buyer lain → 404 (diuji).
- Role `pickup` di AccessService tidak memuat finance/bank/payout — slice ini tidak menambah permission baru (D10 dipatuhi).

### Kontrak orders D16.6 (checklist 3)

- `handover` memanggil `OrdersService.getOrderForHandover(client, tenantId, orderId)` lalu `markHandedOver(client, tenantId, orderId, actorUserId)` dalam **transaksi yang sama** (`:485-495`), lalu menandai kredensial `consumed` dan menulis `order_handovers`.
- Slice pickup **tidak pernah menulis tabel `orders`**: grep menunjukkan tidak ada `UPDATE orders`/`INSERT INTO orders` di `src/modules/pickup/**`; `pickup_credentials`/`order_handovers` juga tidak disentuh modul lain (single writer, D4).
- Konsumsi reservasi terjadi di `markHandedOver` → `availability.consumeReservation` (seat tetap terpakai, `consumed_at`/`updated_at` terisi) — diverifikasi di test dan DB.
- Status `completed` hanya sekali: `markHandedOver` menolak status selain `ready_for_pickup` (`409 ORDER_STATE_CONFLICT`) dan early-return untuk `completed`; `order_handovers_order_unique` + `order_handovers_credential_unique` menutup sisa jalur (probe saya: 2 handover paralel → 1 sukses, 1× 409, 1 baris handover).

### Invariant DB (checklist 4)

- Satu kredensial aktif per order: partial unique `pickup_credentials_one_current_order_unique` (`WHERE revoked_at IS NULL`) — diuji menolak insert kedua (23505).
- `consumed`/`revoked` eksklusif: CHECK `pickup_credentials_consume_revoke_check` — diuji 23514.
- Composite FK `order_handovers(order_id, credential_id) -> pickup_credentials(order_id, id)` menolak handover yang memasangkan order dengan kredensial order lain — diuji 23503.
- `expires_at > created_at` (CHECK 0007) dipatuhi; test sengaja memakai `created_at + interval '1ms'` agar constraint tetap valid saat menguji kedaluwarsa.
- Aplikasi **tidak** hanya mengandalkan validasi sendiri: setiap penulisan tetap melewati constraint (rotate, consume, handover semuanya diuji terhadap DB nyata).

### Idempotensi & balapan (checklist 5)

- Replay handover = **409 konsisten** `PICKUP_CREDENTIAL_CONSUMED`, tanpa efek kedua (event/audit/handover row/versi order tidak berubah) — diuji dua kali berturut-turut dan saya reproduksi.
- Dua handover **paralel** dengan kode sama: tepat **satu** sukses, satu 409, 1 baris `order_handovers`, kredensial `consumed` (probe saya).
- Rotasi mematikan kode lama secara atomik dalam transaksi yang sama (revoke + insert), diuji; probe handover-vs-rotasi menunjukkan state akhir konsisten (order tetap `ready_for_pickup`, kredensial aktif = 1) meski pesan errornya menyesatkan (R3-11).
- `markHandedOver` early-return untuk order `completed` tidak membuka celah: jalur kedua tetap gagal di UPDATE kredensial (`WHERE consumed_at IS NULL`).

### Rate limit (checklist 6)

- Namespace terpisah `antriin:pickup:rate:code` + HMAC-SHA256 IP (IP plaintext tidak pernah masuk Redis); Lua `INCR` + `EXPIRE` pada hitungan pertama (window benar). Probe saya: key sesuai harapan, IP tidak plaintext, TTL 600, ambang 30 → 31 = `429 pickup_rate_limited` + `retry_after` 600, Redis mati → `503 pickup_rate_limit_unavailable` (fail-closed, termasuk saat `ping` gagal), `AUTH_SECRET` hilang → `503 pickup_not_configured`.
- Tidak dapat dilewati dengan variasi format kode: kuota dihitung per IP **sebelum** normalisasi, sehingga huruf kecil/spasi/tanda hubung tidak menambah jatah.
- Guard hanya dipasang pada dua rute yang menerima kode dari pengguna; rute penerbitan/pencabutan tidak memerlukannya (butuh sesi + permission).

### Validasi & error contract (checklist 7)

- `ValidationPipe` global (`whitelist`, `forbidNonWhitelisted`, `transform`) menolak field asing; `PickupCodeDto` memakai `@Matches` pola 4..32 alnum dengan spasi/dash; `RevokePickupCredentialDto.reason` 1..500 (`MAX_PICKUP_REASON_LENGTH`) dan service menolak reason kosong/spasi.
- Status code tepat dan stabil: 409 `PICKUP_CODE_INVALID`/`_REVOKED`/`_CONSUMED`/`PICKUP_NOT_READY`/`PICKUP_HANDOVER_CONFLICT`, 404 `PICKUP_CREDENTIAL_NOT_FOUND`, 410 `PICKUP_CREDENTIAL_EXPIRED` (via `GoneException`), 403 permission, 401 tanpa sesi, 429 rate limit, 503 not-configured/Redis-down.
- Tidak ada pesan yang membocorkan SQL/nama constraint: pesan domain generik; `ApiExceptionFilter` menyembunyikan detail 5xx. Satu-satunya pengecualian adalah 23505 yang tidak dipetakan (R3-03).
- `ApiExceptionFilter` mempertahankan `code` domain (regex mengizinkan huruf kecil) dan menyetel header `retry-after` untuk 429.

### Audit & event (checklist 8)

- Penerbitan: audit `tenant.pickup.credential_issued` + `order_events pickup_credential.issued`; rotasi menambah audit `credential_revoked` + event `pickup_credential.revoked` untuk kredensial lama. Pencabutan: audit + event dengan `reason` wajib dari DTO. Semuanya ditulis **dalam transaksi yang sama** dengan mutasi (gagal audit = rollback).
- Actor selalu dari sesi (`principal.userId`), target = kredensial, scope = tenant; metadata hanya id/waktu/flag, **tanpa plaintext** (diuji dan saya verifikasi).
- `order_events` memakai tipe yang sudah ada di CHECK 0007 (`pickup_credential.issued`/`.revoked`); `request_id` NULL karena slice ini tidak memakai idempotency request (nullable per D12.7) — sesuai.
- Versi event memakai `max(version)+1` dengan asumsi pemanggil memegang lock order `FOR UPDATE`; benar untuk `issueCredential`/`revokeCredential` (keduanya mengunci order lebih dulu), dan handover memakai `OrdersService.appendOrderEvent` di bawah lock yang sama.

### Dokumentasi (checklist 10)

- `docs/modules/pickup.md` akurat untuk: tabel endpoint + permission, model hash/ciphertext, TTL + bounds, aturan rotasi, replay 409, 404 lintas tenant, reason wajib, daftar kode error, dan batasan (tanpa kolom attempt counter, rotasi kunci enkripsi, tanpa outbox pickup). Selisih hanya pada R3-12.

1. Guard brute-force: ambang 429, fail-closed Redis, namespace, hashing IP (menutup R3-02).
2. Konkurensi: dua `handover` paralel dan `handover` vs rotasi (menutup R3-11 dan menjaga properti "tepat satu efek").
3. Lapisan HTTP: 401 tanpa bearer, 403 tanpa `tenant.orders.handover`, 400 DTO, 429, header `Cache-Control: no-store`, dan pemetaan kode error di response.
4. Buyer read untuk kredensial kedaluwarsa dan untuk order yang dibatalkan (R3-05/R3-04).
5. `issueCredential` ketika kredensial `consumed` masih ada (R3-03) — memastikan kode domain, bukan 500.
6. Penerbitan saat `AUTH_ENCRYPTION_KEY` berganti → buyer read 503 `pickup_code_unavailable` (jalur dekripsi gagal belum diuji).
