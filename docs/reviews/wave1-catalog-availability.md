## Yang sudah benar (diverifikasi sendiri, bukan dari laporan implementer)

### Katalog — uang & snapshot (D12/D14)

- Rumus harga persis D12: `unit = base + Σ delta`, `line = unit × qty`, `subtotal = Σ line`, `total = subtotal` (`catalog.service.ts:486-531`). Semua perhitungan `bigint`; keluaran string desimal; tidak ada float/`Number` untuk uang. Overflow > 10^38−1 → 400; total 0 → 400 (D12 butir 5).
- `quote` read-only: probe saya menunjukkan `reserved_count` tetap dan `version` slot tidak berubah setelah quote (D14 butir 7).
- `quoteHash` kanonik: deterministik, reorder baris = hash sama, beda kuantitas/opsi = hash beda (`catalog.service.ts:552-562`); diuji implementer dan lolos.
- Snapshot lengkap: `menuVersion`, `groupVersion`, `optionVersion`, slot `version`, tenant/campus/timezone, nama/deskripsi/kategori, `basePriceMinor`/`unitPriceMinor`/`quantity`.
- `quote` tidak lagi mengunci baris slot (`assertBookableSlot(..., 'none')`, `catalog.service.ts:369-374`): deadlock `quote`→`reserveForCheckout` yang saya laporkan sebelumnya **hilang** — 8 checkout paralel sekarang 8/8 sukses, `reserved_count=8` pada kapasitas 10 (sebelumnya 7 deadlock).

### Katalog — otorisasi, scope, audit

- Setiap mutasi memakai `AccessService.requireTenant(actor, tenantId, 'tenant.menu.manage', client)` di dalam transaksi mutasi, sehingga revoke staf terserialisasi terhadap tulisan.
- Setiap query menyertakan `tenant_id`; resource tenant lain → **404** (bukan 403) sehingga eksistensi tidak bocor; FK komposit menolak referensi lintas tenant (23503). Diuji implementer dan lolos.
- Staf pickup dengan baris grant `tenant.menu.manage` palsu tetap ditolak (AccessService memeriksa role), diuji dan lolos.
- Audit D14 butir 4 lengkap dan transaksional: `tenant.menu.item.price_changed`, `tenant.menu.option.price_changed`, `tenant.menu.item.sold_out|available|archived|restored`, `tenant.menu.category|option_group|option.archived|restored`; `reason` wajib dari DTO (1..300), actor dari sesi, metadata hanya harga/status lama→baru. Test mengasersi urutan aksi+reason+actor secara persis.
- Arsip: tidak ada hard delete; CHECK `archived_at` dua arah (0007) dipenuhi termasuk pengosongan saat reaktivasi; item di kategori terarsip hilang dari discovery dan ditolak quote (D14 butir 2).
- Discovery pembeli publik: hanya `active`/`sold_out`, tanpa data staf/PII, metakarakter LIKE di-escape, cap 200 + `meta.truncated`, 404 untuk tenant archived/kampus nonaktif.

### Availability — kapasitas & konkurensi (D3/D13)

- `reserveForCheckout` memakai `SELECT ... FOR UPDATE` + conditional update `reserved_count < capacity` + CHECK DB, dan **tidak menaikkan `version`** (D3). Probe saya dengan baris `orders` nyata: 12 reserve paralel pada kapasitas 5 → tepat **5 sukses**, 7 gagal 409 "full", `reserved_count=5`, `version` tetap 1.
- Idempotency per order: advisory lock `pg_advisory_xact_lock(hashtextextended(orderId,0))` + unique `slot_reservations_order_unique`; replay paralel mengembalikan reservasi sama tanpa menambah kursi; order sama dengan slot lain → 409.
- Rekonsiliasi R1-18: `reserved_count = COUNT(status IN ('reserved','consumed'))` bertahan setelah gelombang reserve/release/consume campuran; diuji di test dan saya reproduksi sendiri.
- `release`: memulihkan kapasitas tepat sekali, `released_at`+`updated_at` eksplisit, replay = `false` tanpa efek ganda, `consumed` tidak bisa di-release (409), tenant lain → 404.
- `consume`: hanya dari `reserved`, `consumed_at`+`updated_at` eksplisit (memenuhi CHECK 0007), replay = `false`, kursi tetap terpakai. Temuan awal saya (pelanggaran CHECK `consumed_at`) **sudah teratasi** dan saya verifikasi ulang.
- `moveReservation`: dua slot dikunci `ORDER BY id` (anti-deadlock), release+reserve atomik, target penuh/version stale/lintas tenant ditolak tanpa menyentuh slot asal, replay ke slot sama = no-op sukses.
- Penurunan kapasitas di bawah `reserved_count` → **409** "Capacity cannot drop below reserved orders" (bukan 500), diuji dan saya reproduksi.
- Prasyarat FK 0007 (`slot_reservations_order_fk`): didokumentasikan di kontrak (`availability.service.ts:628-641`, `docs/modules/availability.md`) dan slice orders sudah menyesuaikan urutan (`INSERT orders` → `reserve`), saya cek di `orders.service.ts:431-465`. Kontrak lintas slice kini konsisten.

### Availability — otorisasi, audit, validasi

- Semua mutasi manajemen memakai `tenant.capacity.manage` (D10) di dalam transaksi; tenant lain/stranger → 403; scope `tenant_id` di setiap query; tenant archived/kampus nonaktif → 404.
- **Audit (instruksi root terbaru) sudah ada dan benar**: `tenant.availability.slot.created|closed|reopened|capacity_reduced`, ditulis `AuditService.append` dalam transaksi yang sama, actor dari sesi, target `pickup_slot`, `reason` wajib (1..300) untuk close/capacity-down. Probe saya: close tanpa reason → 400; 4 baris audit tertulis dengan actor+target+reason benar.
- Validasi jam operasional memakai **satu** sumber kebenaran D8 (`TenantOperatingHoursService.resolveOperatingWindow`, `availability.service.ts:1035-1053`); modul tidak menulis query sendiri ke tabel operating hours.
- Timestamp respons D7: `to_char(... US"Z")` dari DB, tidak pernah lewat `new Date()`; `expectedVersion` wajib untuk PATCH; `updated_at` di-set eksplisit di setiap mutasi.
- DTO: `whitelist`+`forbidNonWhitelisted`+`transform` global; pola ISO-8601 untuk `startsAt`/`endsAt`; `YYYY-MM-DD` untuk tanggal lokal; `reason` 1..300; status slot hanya berubah lewat aksi manajemen berizin (tidak pernah dari body sebagai otoritas status order/harga).
- Dokumentasi `docs/modules/availability.md` sudah diselaraskan: audit, `consumed_at`/`updated_at`, lock modes `none/share/update` beserta alasan deadlock 40P01, prasyarat FK orders, formula rekonsiliasi. `docs/modules/catalog.md` akurat terhadap kode (rumus, audit, arsip, endpoint, batasan kategori tanpa kolom version).
- Error contract: semua error domain memakai `HttpException` sehingga `ApiExceptionFilter` menghasilkan `{error:{code,message,request_id}}`; tidak ada pesan yang membocorkan SQL/nama constraint mentah.
